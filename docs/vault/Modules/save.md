# Modules/save

> [!abstract] Role
> One localStorage key, versioned, with a migration function from the first shape change onward (brief §8 "Save and share"). Owner: Systems Engineer.

## What it does

`src/save/save.ts` — `SAVE_KEY` = `gravity-works.save`, `SAVE_VERSION` = 2, and `MIGRATIONS[i]` upgrades a save at version `i` to `i + 1`; `loadSave` runs every migrade between the stored version and the current one, so "no key at all" is version 0 and flows through the first migrade — which is exactly how it was written from day one (`MIGRATIONS.length` equals `SAVE_VERSION`, asserted in test). The v2 envelope is `{ v, builds, settings, progress }` (v1 was `{ v, builds, settings }`), and each `builds[levelId]` is the canonical `serialize` JSON text from `src/track` — never a live `Build` object, because a `THREE.Matrix4` mangles itself into `{"elements":…}` through a plain `JSON.stringify` (caught by test, not by theory). `coerceBuild` normalises both legacy transform shapes before adopting anything.

The stage-4 `progress` record (`SaveProgress`) is the campaign's whole memory and the ONLY data `src/world/campaign.ts`'s `levelUnlock` reads (since the garage close-out the table carried FIVE rooms, SIX since the porch close-out, and since the stage-6 T3.1 re-weave it is a FLAT woven ladder with the rooms as a projection (`[[Concepts/Levels]]` §Ordering of the ladder) — and the rule is UNCHANGED: every later rung unlocks on the same previous-rung star, `bathroom04` minting `garden01` and `garden04` minting `garage01`, `garage04` minting `porch01`, `porch05` last): `stars[levelId]` is the best count ever EARNED, written by `recordStars` at a terminal run status (`src/boot.ts`; best-per-level, clamped 0..3, and a 0-star failure records NOTHING — §9.2 gates on stars, not on trying), and `reached[levelId]` is a LEGACY carry written ONLY by the v1→v2 migrade: `MIGRATIONS[1]` takes a v1 save (which counted no stars — its only trace of where a player stood was the per-level build autosave), keeps every byte of `builds`/`settings`, and marks `reached` for exactly the levels that HAD a build record. That carries a kitchen-era player's kitchen open (no re-locking a finisher behind `kitchen01`) and opens NOTHING that v1 had not already made reachable: a kitchen-only save's bedrooms gain no mark and stay gated on the previous rung's star (since the re-weave: `bedroom01` on `kitchen03`'s), and no stars are minted from old bytes (a migration cannot know what a run scored; trophies nobody earned are banned — `Sessions/2026-10-07 Stage 4 - room picker`). `reached` is never written again: placing a piece in a v2-era save cannot open a door.

Garbage never crashes the game, and since T0.3 (stage-7 program, engineering R1) it is never SILENT either: `migrateDetailed` reports `damaged` (anything had to be dropped/repaired to make the envelope readable — `normalizeEnvelope` walks `builds`/`stars`/`reached` PER KEY, so ONE bad build among good keeps every good entry instead of wiping the save whole) and `usable` (nothing salvageable at all). On any damaged read `loadSave` first QUARANTINES the raw bytes — `quarantineRaw` stashes them OUTSIDE the envelope under `gravity-works.save.corrupt-<n>` (`CORRUPT_KEY_PREFIX`, monotonic counter key, deduped, capped at `QUARANTINE_CAP` = 5) — then lets the game play on the repaired/fresh envelope, and `listQuarantined` is what the Settings row (`src/ui/settings.ts`) shows as the ONE honest line plus per-copy restore buttons. The corrupt bytes leaving the envelope is the whole trick: `SAVE_VERSION` stays 2 and v3 stays reserved for F6 (pinned in test), no schema bump, no data destroyed. From-the-future envelopes: the LIVE path refuses (and quarantines) — reserved means reserved — while SALVAGE (`salvageBlob`, the import/restore path) takes a future blob at face value IF it validates, clamping `v` down: the evaluator's v3 save with two banked stars is recoverable bytes, not a wipe. `saveFileJson`/`importSaveFile`/`downloadSaveFile` move the same envelope through a file (brief's export/import, wired to the UI since T0.3); `importSaveFile` VALIDATES BEFORE ACCEPTING — an unreadable file throws and the live save survives, it never becomes the wipe it was meant to undo. Writes carry the T0.6/R9 law: `builds` entries may be `{t, s}` and `progress.stars` entries `{t, n}` records INSIDE the v2 envelope (`t` = wall-clock ms; plain string/number is the same record at stamp 0 — every reader accepts both, `isSaveData` tolerantly), `saveSave` is a merge-WRITE (re-reads the on-disk records, stamps the keys THIS write changed, revives keys a stale view never saw, verify-and-re-merge once against the read→write hop; settings stay last-writer) so two tabs racing bursts cannot lose each other's records — no lease, no `rev` bookkeeping; `replaceSave` is the deliberate install path only (import/restore). `memoryStorage` is the injectable `StorageLike` that makes the whole module run under Vitest with no DOM; `rememberBuild`/`savedBuild` and `recordStars` are the game-facing trio (`src/boot.ts` autosaves and scores through them — and since the stage-4 R+S pass LOADS through them too: `startBuildFor` restores a level's autosaved working build on boot unless the URL addresses a build (`?build=par`/`alt`) or the save holds no record for that level — the autosave stopped being write-only the day a reload silently wiped a playtester's in-progress build). Since the T round4 pass the boot-side write goes through `createBuildAutosave(remember, delayMs = 350, clock)`: one `rememberBuild` per EDIT BURST (every place/remove replaces the pending build and restarts the trailing window) rather than a full-envelope rewrite per mutation, with `flush()` wired to `pagehide` and visibility-hidden so a reload inside the window still stores the LAST edit — the autosave is EDIT-SIDE, never run-end (playtest T's "reload kept 1 of 3"); a level change is a cross-document navigation, so no pending edit ever survives a boot, and cross-level isolation stays entirely in the level-keyed `builds` record + `startBuildFor`'s foreign-record refusal (a kitchen burst writes `builds.kitchen01` and nothing else); KNOWN DEFERRED HAZARD (close-review F6): `startBuildFor` checks `saved.levelId === level.id` and NOTHING ELSE, so a build autosaved before a level-geometry re-cut restores stale piece transforms onto the new deck (stage 4 moved decks under existing saves twice — L02 fail-timing, bedroom02 B2; deterministic and Remove-unwindable, but the current tray may not be able to produce the restored build) — the fix direction is stamping `builds[id]` with a level-geometry revision (or the par hash) and refusing a mismatch, a versioned migration deliberately deferred to stage 5 (Home Deferred, `Reference/Review 2026-10-09 stage 4 close.md`); `saveFileJson`/`importSaveFile`/`downloadSaveFile` move the same envelope through a file (brief's export/import — and since T0.3 the Settings row is their UI).

`SaveSettings` is `{ muted?, reducedMotion?, calloutsSeen?, sound? }` — `calloutsSeen` (stage 3) is the list of first-sight callout ids already shown, owned by `src/ui/callouts.ts`; optional by design, so an absent list means "nothing seen yet" and the envelope stays v1 — no migrade needed. `sound` (stage 5, `SoundSettings` = `{ muted?, volume? }`) is the mute/volume pair `src/sound/sound.ts` reads and writes — the SAME optional-key technique (absent means defaults), so it too needs no version bump: `isSaveData` validates `settings` as an object and passes unknown keys through untouched, and the v3 migrade F6 wants for the autosave-revision fix stays unblocked. The round-trip at unchanged `SAVE_VERSION` is asserted in `tests/unit/sound.test.ts`.
