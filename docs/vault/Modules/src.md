# src (app root)

> [!abstract] Role
> The browser entry point and shell of Gravity Works. Stage 2 replaced the placeholder with the real game shell: a fixed-timestep loop around the `World`, the builder tray, and a share-replay verification page.

## What it does

`src/main.ts` queries `#app` and hands it to `src/boot.ts` — unless the URL carries `?harness=1`, in which case it lazily imports `src/dev/harness.ts` instead (the deterministic render harness; see the dev module note) — and imports `src/ui/shell.css`, the interim shell skin. `src/boot.ts` then branches on the URL: a `#s=` share fragment opens the shared-run page, which SINCE STAGE 5 opens INTO A CINEMATIC REPLAY — the recorded shot-sequence player over `src/replay/cinematic.ts` (record the run step-for-step, render WIDE/FOLLOW/FINISH with the scrubber, post stack riding along, "Build your own" exit; see [[replay]] for the seek law) — while the headless verification keeps its exact contract (`replayRun` vs the embedded hash in `#gw-replay-status`, now in the `#gw-replay-verify` block BELOW the player, the hash talk off the fold), and (stage 3) the share-card download (`#gw-share-card` → `src/share/card.ts`) rides along in that block; since stage 4 a `?levels` param renders the LEVEL SELECT page instead of a game (`createLevelSelect`, `src/ui/levelselect.ts` — the rooms, rungs, stars and locked-reason copy in `Modules/ui`; the game shell links to it as `#gw-levels-link`, "All levels", and the link is honest because every build is already autosaved on change); anything else boots the game — the level's STARTING build in a `World`, an accumulator-driven 120 Hz loop whose renderer reads only `states()` + alpha, the builder UI (autosaved on edit through `createBuildAutosave`, whose write is `rememberBuild` — debounced per edit burst and flushed before the unload, T round4), and `runStatusLine` as the aria-live run copy (since the P+Q pass the idle line states the tray tally in the tray's own words — "ready — n of m pieces used", one counter one verb; see [[ui]]). The game starts EMPTY of tray pieces: `initialBuild(level)` mounts only the level's built-in FIXTURES (filtered from `parBuild()`) and leaves the tray pieces in the tray for the player (`?build=par` re-mounts the full placeholder/reference build for the test rigs — the pre-built default was the deployed-page bug that pre-played the tutorial and read "5 / 3 pieces"; `?build=alt` re-mounts a CHOICE level's ALTERNATE authored line — boot's `ALT_LINES` addressing table maps `kitchen02` to the module's existing `kitchen02ArcBuild` export so the filmstrip gate frames BOTH lanes of Two Ways without any level-data edit, and a level with no entry falls back to its normal start build). The two ladder-coherence seams live beside it: `levelTrayParams` (the geometry a tray button ghosts and seats with — the level's declared `trayParams` first, the par build's tuned first-placement per kind on top) and `trayParityBuild` (the build the builder would produce if the player placed the par line: fixtures anchored, tray pieces seated at that one geometry — a probe for `tests/unit/kitchen-levels.test.ts`, never a runtime path; a coherent level's is byte-identical to `parBuild()`). `playerPieceCount` is the same fixtures-excluded tally `Builder.playerCount` reports live, and it is what the share-card star line scores a replayed build with — `pars.json`'s `parPieces` is on that TRAY basis too (`scripts/gen-pars.mjs`), which is the fix for the deployed panel's "3 pieces — par 5" on a three-piece tutorial. Between runs the static camera frames the TRACK group alone, biased 35 % of the look-at toward the build's finish-cup capture centre (stage 4 watchability: at box-centre framing the goal sat at the frame's edge where playtest N never found it; `frameCamera` is exported so the goal-framing proof in `tests/unit/camera.test.ts` can assert it); during a run the §7.3 `RunCamera` over the build's `KitRig` rail owns the transform, and at a terminal status it HANDS THE VIEW BACK to the static framing (the post-run rail freeze-frame was the deployed "camera buried inside the floor") — the hand-back END-HOLD framing also boxes the car's final position (clamped to the track's ±0.6 m neighbourhood) into the subject, so the verdict panel never lands over an off-frame death spot (playtest M item 6); since playtest R round 3 a FAILED run instead hands to `frameDeathHold` — the wide death-site hold (see [[camera]]) — with the witness held through the damping tick, and the build view gained an `Escape Escape` recenter (see [[camera]]). The canvas element sizes to the stage through `#gw-stage canvas` — `renderer.setSize(960, 540, false)` writes the buffer without the inline style that used to override that rule and hold the page taller/wider than any laptop viewport (the letterbox half of the 3/3 "panel invisible" finding; the panel itself centres on the stage and `scrollIntoView`s on show); since the shell-truth pass the rule also caps the element at the 960 px BACKING width (`max-width: 960px` — a stage-wider upscale quietly broke the idle visual baseline) and the shell renders one static warm frame straight after mount so the canvas is never black while `World.create` awaits the physics wasm. The builder DOM sits ABOVE the canvas so clicking Launch cannot scroll the world out of the viewport, and since the R+S pass it is STICKY (`#gw-builder-host` is `position: sticky; top: 0` with a z-index above every stage overlay): the "Remove clicks died behind the result card" dead toolbar was SCROLL, not z-order — a scrolled page pushed the toolbar off-screen and the blind click at its old position hit the canvas THROUGH the pointer-transparent panel — so the toolbar is now always on screen and always the thing under the cursor while a result card is up (`tests/e2e/playtest-rs.spec.ts` audits both), and the game's start line resolves through `startBuildFor`: a revisit of a level the player is working in RELOADS the autosaved working build (`savedBuild`), while `?build=par`/`?build=alt` addressing and levels with no record start fresh (playtest S's silently-wiped rebuild). and the closed loop is wired here: `#gw-reset` (beside Launch) and the panel's Retry both call `World.reset()` + the static framing (car home, build kept), the panel's Next walks `LADDER` via `nextLevelId` — since stage 4 an export over the CAMPAIGN table (`src/world/campaign.ts`: the five rooms kitchen → bedroom → bathroom → garden → garage concatenated, `kitchen01..05`, `bedroom01..04`, `bathroom01..04`, `garden01..04` then `garage01..04`, so the boundary steps `kitchen05 → bedroom01`, `bedroom04 → bathroom01`, `bathroom04 → garden01` and `garden04 → garage01` are ordinary steps and `garage04` has no next — the campaign's final rung; off-ladder surfaces have no next) — and is STAR-GATED by `gateNext` (it appears when the SAVE holds a star for the rung — the max of this run's stars and the banked best, close-review F5, so panel and level select cannot disagree; a 0-star failure on an unstarred level gets Retry only); the same terminal status also calls `recordStars(level.id, model.stars)` (`src/save`), the persistence that turns that session gate into a CAMPAIGN: the saved best-per-level is what `levelUnlock` (campaign) opens the level select on, and a 0-star failure records nothing. `__gwCameraPose` is the e2e seam the follow assertion reads. The stage-3 post hook is a no-op unless `?post=on`: only then does the shell dynamically import `createPostStack` and render the frame through the composer with the focus band centred on the car; the default page keeps the stage-2 `renderer.render` line. Level resolution goes through `getLevel`: `?level=<id>` selects any registered level (shares resolve the same way), and the DEFAULT is `kitchen01` — the ladder's first rung — with the feel track reachable as `?level=feeltrack` (the stage-2 builder/result/perf specs use it).

Stage-3 set mounting, generalized at stage 4 through the set registry ([[sets]]): a level declaring `set: 'kitchen'` gets its `SetInstance` (from `src/sets/index.ts`, whose `build` DYNAMICALLY imports the mounted set's builder module — the stage-4 payload fix: boot evaluates only the set it mounts, while the token rows and placement tables stay static for the warm frame and the grade; see [[sets]] — which wraps `buildKitchenSet` and `kitchenSetPlacement`) mounted into the world's scene as a SIBLING of the track group, placed by the registration's `placement(level.id)` — visual only, no colliders, built once per boot and detached (not disposed) before `world.dispose()` so its materials survive track rebuilds; the stage element carries `data-set-mounted` with the SET's id (kitchen frames unchanged). A dev entry `?set=<registered-id>` overrides the level's declaration in the game shell (`?set=bedroom` walks the bedroom props through a kitchen level's physics) — and because the mount is registry-keyed, a level declaring `set: 'bedroom'` mounts the bedroom with no boot edit (same since the bathroom pass for `set: 'bathroom'` — the registry rows are the only wiring a new set needs); the warm first frame, the mounted background and the `?post=on` grade tokens all read the registration's tokens (kitchen values unchanged as the fallback). The same mounted dress feeds the builder's `solids` guard (`setPlacementGuard` — the dress/shell naming convention is documented in `src/sets/index.ts` and `collectSetBoxes`), grip samples below 1 during a run tally into the result screen's `hazardsTouched`, and `world.hazardZones` is exposed to e2e as `__gwHazardZones`.

The stage-3 run-end layer rides the same loop: every fixed step feeds `createRunRecorder().sample(w.state())`, and when the status turns terminal the shell shows the end-of-run panel once (`createResultPanel`/`resultModel`, `src/ui/result.ts`) with stars scored by `starsFor` against `parFor` and the running build's piece-kind set (build-aware note tails — see [[ui]]) (generated pars, `src/world`)
Since playtest U round 4 the shell also carries the `__gwGoalNdc` e2e seam: the current build's FINISH CUP capture centre (`finishCapture`, the same point the static framing biases toward) projected through the LIVE render camera to normalised device coords — the goal-in-frame sweep in `tests/e2e/playtest-tu.spec.ts` walks all 21 campaign rungs on it (debug surface, not UI; see [[camera]]). and the par lines printed beside the tallies — the panel is hidden during runs (§5.11) and re-hiding is also what an edit does to a stale result. Placing a piece of a kind never placed before raises its one-line callout (`firstSight`, `src/ui/callouts.ts`, recorded in the save); the help drawer (`createHelpDrawer`, `src/ui/help.ts`) is hosted OVER `#gw-stage` — quiet top-right toggle, overlay list. `?launch=1` releases as soon as the first world is ready — the test hook `tests/e2e/result.spec.ts` drives the whole finish-the-run loop with, and nothing else reads it. These params (`?level=`, `?build=par`, `?build=alt`, `?launch=1`) are DEBUG AFFORDANCES on the shipped page, deliberately recorded rather than DEV-stripped — the whole e2e rig drives the production build through them, and the ladder gates what a player EARNED (`gateNext`'s star rule), not what a URL can ADDRESS: no param forges a star, a save, or a share (Decision Log 2026-10-07, "shipped page keeps its URL debug affordances").

## How it works

No router, no framework (per the brief's "small entity model, not a framework"). The fixed step lives in physics (`World.step`); the frame loop only decides *how many* fixed steps the elapsed time pays for (capped, so a background tab cannot fast-forward a run). Pure bits of the shell (`runStatusLine`, `nextLevelId`) are unit-guarded by `tests/unit/boot.test.ts` (the status line carries no hash since the shell-truth pass — the fingerprint lives in the `#gw-hash-details` disclosure); the DOM/canvas half by `tests/e2e/smoke.spec.ts`, `tests/e2e/builder.spec.ts` (whose expected piece counts import the level data — `FEEL_TRACK_KINDS.length`, `FEELTRACK.budget` — instead of mirroring it), `tests/e2e/result.spec.ts` (finish → panel; help drawer opens and renders), `tests/e2e/campaign.spec.ts` (the stage-4 room picker: boundary Next, locked-rung-says-why, unlocked-by-earned-star, real-UI bedroom01 finish, error-free set switch), `tests/e2e/loop.spec.ts` (the playtest-fix gate on the BUILT app), `tests/e2e/shell-truth.spec.ts` (the playtest E/F/G gate: keyboard-only L01 build, star-gated Next, non-black first paint, visible rotate) and the share-verified e2e.
