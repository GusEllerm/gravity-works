# src (app root)

> [!abstract] Role
> The browser entry point and shell of Gravity Works. Stage 2 replaced the placeholder with the real game shell: a fixed-timestep loop around the `World`, the builder tray, and a share-replay verification page.

## What it does

`src/main.ts` queries `#app` and hands it to `src/boot.ts` — unless the URL carries `?harness=1`, in which case it lazily imports `src/dev/harness.ts` instead (the deterministic render harness; see the dev module note) — and imports `src/ui/shell.css`, the interim shell skin. `src/boot.ts` then branches on the URL fragment: a `#s=` share fragment opens the shared-run page, which replays the payload headlessly through `src/replay` and prints `verified`/`mismatch` against the embedded hash, and (stage 3) wires the share-card download (`#gw-share-card` → `src/share/card.ts`); anything else boots the game — the level's STARTING build in a `World`, an accumulator-driven 120 Hz loop whose renderer reads only `states()` + alpha, the builder UI (autosaved via `rememberBuild`), and `runStatusLine` as the aria-live run copy. The game starts EMPTY of tray pieces: `initialBuild(level)` mounts only the level's built-in FIXTURES (filtered from `parBuild()`) and leaves the tray pieces in the tray for the player (`?build=par` re-mounts the full placeholder/reference build for the test rigs — the pre-built default was the deployed-page bug that pre-played the tutorial and read "5 / 3 pieces"). The two ladder-coherence seams live beside it: `levelTrayParams` (the geometry a tray button ghosts and seats with — the level's declared `trayParams` first, the par build's tuned first-placement per kind on top) and `trayParityBuild` (the build the builder would produce if the player placed the par line: fixtures anchored, tray pieces seated at that one geometry — a probe for `tests/unit/kitchen-levels.test.ts`, never a runtime path; a coherent level's is byte-identical to `parBuild()`). `playerPieceCount` is the same fixtures-excluded tally `Builder.playerCount` reports live, and it is what the share-card star line scores a replayed build with — `pars.json`'s `parPieces` is on that TRAY basis too (`scripts/gen-pars.mjs`), which is the fix for the deployed panel's "3 pieces — par 5" on a three-piece tutorial. Between runs the static camera frames the TRACK group alone; during a run the §7.3 `RunCamera` over the build's `KitRig` rail owns the transform, and at a terminal status it HANDS THE VIEW BACK to the static framing (the post-run rail freeze-frame was the deployed "camera buried inside the floor"). The canvas element sizes to the stage through `#gw-stage canvas` — `renderer.setSize(960, 540, false)` writes the buffer without the inline style that used to override that rule and hold the page taller/wider than any laptop viewport (the letterbox half of the 3/3 "panel invisible" finding; the panel itself centres on the stage and `scrollIntoView`s on show); since the shell-truth pass the rule also caps the element at the 960 px BACKING width (`max-width: 960px` — a stage-wider upscale quietly broke the idle visual baseline) and the shell renders one static warm frame straight after mount so the canvas is never black while `World.create` awaits the physics wasm. The builder DOM sits ABOVE the canvas so clicking Launch cannot scroll the world out of the viewport, and the closed loop is wired here: `#gw-reset` (beside Launch) and the panel's Retry both call `World.reset()` + the static framing (car home, build kept), the panel's Next walks `LADDER` via `nextLevelId` (kitchen01…05; off-ladder surfaces have no next) and is STAR-GATED by `gateNext` (it appears only when the finished run earned ≥ 1 star — a 0-star failure gets Retry only), and `__gwCameraPose` is the e2e seam the follow assertion reads. The stage-3 post hook is a no-op unless `?post=on`: only then does the shell dynamically import `createPostStack` and render the frame through the composer with the focus band centred on the car; the default page keeps the stage-2 `renderer.render` line. Level resolution goes through `getLevel`: `?level=<id>` selects any registered level (shares resolve the same way), and the DEFAULT is `kitchen01` — the ladder's first rung — with the feel track reachable as `?level=feeltrack` (the stage-2 builder/result/perf specs use it).

Stage-3 set mounting, generalized at stage 4 through the set registry ([[sets]]): a level declaring `set: 'kitchen'` gets its `SetInstance` (from `src/sets/index.ts`, which wraps `buildKitchenSet` and `kitchenSetPlacement`) mounted into the world's scene as a SIBLING of the track group, placed by the registration's `placement(level.id)` — visual only, no colliders, built once per boot and detached (not disposed) before `world.dispose()` so its materials survive track rebuilds; the stage element carries `data-set-mounted` with the SET's id (kitchen frames unchanged). A dev entry `?set=<registered-id>` overrides the level's declaration in the game shell (`?set=bedroom` walks the bedroom props through a kitchen level's physics) — and because the mount is registry-keyed, a level declaring `set: 'bedroom'` mounts the bedroom with no boot edit; the warm first frame, the mounted background and the `?post=on` grade tokens all read the registration's tokens (kitchen values unchanged as the fallback). The same mounted dress feeds the builder's `solids` guard (`setPlacementGuard` — the dress/shell naming convention is documented in `src/sets/index.ts` and `collectSetBoxes`), grip samples below 1 during a run tally into the result screen's `hazardsTouched`, and `world.hazardZones` is exposed to e2e as `__gwHazardZones`.

The stage-3 run-end layer rides the same loop: every fixed step feeds `createRunRecorder().sample(w.state())`, and when the status turns terminal the shell shows the end-of-run panel once (`createResultPanel`/`resultModel`, `src/ui/result.ts`) with stars scored by `starsFor` against `parFor` (generated pars, `src/world`) and the par lines printed beside the tallies — the panel is hidden during runs (§5.11) and re-hiding is also what an edit does to a stale result. Placing a piece of a kind never placed before raises its one-line callout (`firstSight`, `src/ui/callouts.ts`, recorded in the save); the help drawer (`createHelpDrawer`, `src/ui/help.ts`) is hosted OVER `#gw-stage` — quiet top-right toggle, overlay list. `?launch=1` releases as soon as the first world is ready — the test hook `tests/e2e/result.spec.ts` drives the whole finish-the-run loop with, and nothing else reads it. These three params (`?level=`, `?build=par`, `?launch=1`) are DEBUG AFFORDANCES on the shipped page, deliberately recorded rather than DEV-stripped — the whole e2e rig drives the production build through them, and the ladder gates what a player EARNED (`gateNext`'s star rule), not what a URL can ADDRESS: no param forges a star, a save, or a share (Decision Log 2026-10-07, "shipped page keeps its URL debug affordances").

## How it works

No router, no framework (per the brief's "small entity model, not a framework"). The fixed step lives in physics (`World.step`); the frame loop only decides *how many* fixed steps the elapsed time pays for (capped, so a background tab cannot fast-forward a run). Pure bits of the shell (`runStatusLine`, `nextLevelId`) are unit-guarded by `tests/unit/boot.test.ts` (the status line carries no hash since the shell-truth pass — the fingerprint lives in the `#gw-hash-details` disclosure); the DOM/canvas half by `tests/e2e/smoke.spec.ts`, `tests/e2e/builder.spec.ts` (whose expected piece counts import the level data — `FEEL_TRACK_KINDS.length`, `FEELTRACK.budget` — instead of mirroring it), `tests/e2e/result.spec.ts` (finish → panel; help drawer opens and renders), `tests/e2e/loop.spec.ts` (the playtest-fix gate on the BUILT app), `tests/e2e/shell-truth.spec.ts` (the playtest E/F/G gate: keyboard-only L01 build, star-gated Next, non-black first paint, visible rotate) and the share-verified e2e.
