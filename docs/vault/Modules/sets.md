# src/sets (the set registry + the production bedroom set)

> [!abstract] Role
> The stage-4 generalization of the stage-3 kitchen wiring: `src/sets/index.ts` resolves a set id to its builder, tokens, and per-level mount, so every later set (garden, garage, porch) mounts by data instead of by a new code path. Also the home note of the PRODUCTION bedroom set — variant B, lamp-lit dusk hardwood, ratified 13/13 at both canonical cameras — with the three mid-distance story props that answer the AD's "no single prop carries the frame" caveat.

## The SetInstance surface

`SETS` maps `"kitchen"` / `"bedroom"` / `"bathroom"` / `"garden"` (later: garage, porch) to a `SetRegistration`: `tokens`, `build(T, opts)` → `Promise<SetInstance>`, and `placement(levelId)` → the mount transform (null = canonical origin). `build` is LAZY by design (stage 4 payload fix): it DYNAMICALLY imports the set's builder module, so boot evaluates only the mounted set's geometry module — the eager five-module chain put every set into every page load (CI boot-time diff ~2x on boot-heavy e2es once the garage row landed) while exactly one set mounts per boot; the token rows (`BATHROOM_TOKENS`, `GARAGE_TOKENS`, `SET_TOKENS`) and the placement tables stay static so the warm first frame and the post grade read them before the set module fetches, and the one caller (`buildGameSet` in `src/boot.ts`) simply awaits — the mount rides boot's existing async line. `SetInstance` is the kitchen's stage-3 export shape normalized: `{ group, sockets, hazardZones, bounds, staging }` — solid boxes for the builder guard are collected from the named props by the walker in `src/boot.ts`, sockets are named snap frames, `hazardZones` is plain data in the level hazard shape, `bounds` is the floor surface every socket/hazard must live inside.

The naming convention the guard depends on (documented at BOTH ends — `src/sets/index.ts` and `collectSetBoxes` in `src/boot.ts`): props live under a group named `dress`, the non-solid floor/wall shell lives OUTSIDE it (the kitchen's named `counter`, the bedroom's named `shell`), and anything named `*film*` is never a solid. A set that renames `dress` silently mounts invisible to the placement guard — this is the registry's sharpest edge and the friction named for the next three mounts. Since the stage-6 kitchen03 pass the convention carries a PLAYER-facing weight it did not have: `setPlacementGuard` returns the guards WITH those paths (`SetGuard { name, box }`, the camera walk mapping them back to `.box`) and `solidWord` in `src/ui/builder.ts` turns the first path element into the noun of the refusal the player reads ("blocked — the cereal bowl is in the way"), so a rename is now a COPY bug as well as a guard hole, and a group that simply goes un-named loses the specific line and falls back to the shipped generic wording (`tests/unit/set-wiring.test.ts` proves every guard path resolves to a named object under the mounted set's `dress`).

Adapters kept honest: the kitchen's floor surface is named `counter` and its placement table is `kitchenSetPlacement` — the registry's kitchen row is the one translation (`counter` → `bounds`), and the kitchen rows are re-derived whenever a rung's geometry moves (the kitchen02 row followed its stage-4 discoverability and fail-timing rebuilds, and the kitchen03 row followed its stage-5 K3 re-sweep — the table is a live derivation, not a fossil); the bedroom row (stage 4) places through `bedroomSetPlacement` — four rows, one per shipped bedroom rung, the mount rule recorded in [[world]] and [[Concepts/Levels]]; the bathroom row (stage 4, bathroom pass) is the same shape through `bathroomSetPlacement` — its floor surface is named `floor` and its wider corridor offset is derived (not guessed) in `src/world/setPlacement.ts` (row landed with `Sessions/2026-10-08 Stage 4 - bathroom ladder.md`; it is what `?set=bathroom` and a `set: 'bathroom'` level resolve through); the garden row (stage 4, garden pass) flipped from the registry's documented `() => null` ("no level placements") to `gardenSetPlacement` — four rows on the same rule with the widest offset of the sets (`GARDEN_AXIS_OFFSET` −0.52 m, the flush-paving `DECK_Y` surface riding under the lowest authored deck; landed with `Sessions/2026-10-08 Stage 4 - garden ladder.md`), and the set module registers the `prop:shadowBars` / `prop:sprinkler` first-sight callouts the garden ladder's cards lean on; the porch row (stage 5, production port of ratified variant A) is exported as the named `PORCH_SET` registration and mounted as `SETS.porch` — its `build` resolves `src/sets/porch` the same lazy way, its floor surface is named `ground` (the deck disc), its sockets are the threshold triple `door.in` / `door.out` / `step.out` (`PORCH_SOCKET_FRAMES`), its `placement` is `porchSetPlacement` (FIVE rows since the stage-5 porch ladder — the same mount rule, `PORCH_AXIS_OFFSET` −0.53 m derived from the forward-most dress solid, the roof corner posts, by `tests/unit/porch-levels.test.ts`), the door assembly and the gutter flume are SHELL geometry so the corridor stays fully buildable, and the module registers the `prop:weaveShadow` / `prop:gutterFlume` callouts.

## The bedroom set

`src/sets/bedroom/data.ts` is the pure-numbers half (no three import), migrated from the ratified exploration `src/dev/scenes/bedroom.ts` (variant B): `FLOOR` + `insideFloor`, `CARD_GAP` (a 0.856 m credit card at 1:64), `LAMP` (position, `bulb` point, `reach`/`intensity`/`decay` — tuned STEEP and SHORT, see the data note: r186 punctual scale washes a dusk room at gentler falloff), `DESK` (four visible legs + apron — the floating-slab material note, paid), `DRESSER` + `DRAWER_SOCKET_FRAMES` (`drawer.in` / `drawer.out`, bored cabinet, `boreY` hung one `CARD_GAP` under the opening's jaw), `BOOK_PYRAMID` (tiers, book dims, seeded lean), `BED`, `CABLE`, `HOMEWORK` (the lived-in detail moved INTO the floor band), `SEAMS`, `HAZARDS` (empty — variant B ratifies none, but the surface carries the field), `STAGING` (the one decorative run + the still's car parameter).

`buildBedroomSet(THREE, opts)` in `src/sets/bedroom/index.ts` returns `{ group, sockets, hazardZones, floor, staging, lampLight }`. The deliberate deviation from the kitchen's "no lights" contract: **the lamp is a practical** — a `THREE.PointLight` named `lamp-practical` inside the shade at `LAMP.bulb`, so the warm pool is lit, not painted; the render rig's shadow-casting key sits at the same origin (one direction explains every shadow). The shader-side guarantee is the punctual gate in `src/render/toon-material.ts` (see [[render]]): without it, the practical re-adds the key-strength tint everywhere it fails to reach and the frame washes like the stage-3 kitchen.

## The bathroom set

`src/sets/bathroom/data.ts` + `src/sets/bathroom/index.ts` are the PRODUCTION bathroom set — variant A, the porcelain cathedral (AD 14/15/15 at both canonical cameras, `Reference/Review 2026-10-08 Stage 4 bathroom+bedroom.md`), ported from the ratified dev exploration `src/dev/scenes/bathroom.ts` by the LEVEL DESIGNER as a minimal art port at the stage-4 kickoff (the kitchen/bedroom pattern; the port's friction — class-ramp thresholds, the scene-owned key rig, the shadow extent — is stated in `Sessions/2026-10-08 Stage 4 - bathroom ladder.md`, not tuned away). Shape: `FLOOR` (a ring-tiled disc) + `SURFACES`, `TILES`, `TUB` (rim towel and rubber duck riding it), `DRAIN` (a floor-mounted chrome ring OFF the lane — the tunnel-mouth story), `TOOTHBRUSH`, `SOAPDISH`, `TOWELS`, `DRIPS` (the ratified wet-patch FILM pair — decoration only: live wet-patch zones are LEVEL data, ask #6), `STAGING` (the dev scene's one decorative run + the still's car; levels never import it). `SOCKETS` and `HAZARDS` are deliberately EMPTY — the ratified variant names no prop socket (the drain is a mouth, not a bore: the kitchen-tap convention, a plain anchor marks, nothing snaps) and the set ships no live zone; both fields exist typed for the `SetInstance` surface. Two prop positions moved from the dev scene with the reason documented in the file (towel bar and soap dish pulled off the set-origin corridor the dev track ran through — production lanes mount behind the cluster; `tests/unit/bathroom-levels.test.ts` asserts every prop box clears the four rungs' guard boxes). The `build(T, opts)` opts carry the ratified KEYLIGHT rig (position + hex + shadow-map size — the dev scene owns these values, the registration passes them through); the shadow extent stays a RENDER-rig concern — `createRenderKit`'s ortho extents are kitchen-sized, documented as a later-set rig task, not silently grown. The set registers the `prop:wetPatch` first-sight callout into `PROP_CALLOUTS` (`src/ui/callouts.ts`) — the lesson Playtest G never found on L04.

`src/sets/garden/data.ts` + `src/sets/garden/index.ts` are the PRODUCTION garden set (stage 4, the studio's first outdoor set — the sun/sky regime lives in its data: `SUN`, `SKY`, `FILL_STRENGTH`, `SKY_INFLUENCE`, and since the round-1 production send-back the fill-shadow dials `FILL_SHADE_DEPTH` + `STONE_FILL_SCALE` and the re-framed `CAMERAS.floor`; `Reference/Review 2026-10-08 Stage 4 garden production.md` is the send-back it answers).

## The porch set

`src/sets/porch/data.ts` + `src/sets/porch/index.ts` are the PRODUCTION porch set (stage 5) — variant A, sunday morning, ratified 15/16 with a same-day production check that found no send-back (`Reference/Review 2026-10-09 porch judging.md`), ported from the exploration `src/dev/scenes/porch.ts` porch-a by the Environment Artist as a MIGRATION, not a redesign (`Sessions/2026-10-09 Stage 5 - porch production set.md`). The light regime is the garden's ported indoors-by-half: `SUN` is a low (~14°) WARM directional key (`keyColor: '#FFE3B8'`, never the indoor lamp key) and the flat `SKY` is the fill through `createLightingRig`, plus the porch's ONE addition — `porchFillFromRig` with `SHADOW_TINT_SKY_LIFT` 0.85, the exploration's round-3 finding promoted from a scene-local override to set data (cast shade is a big soft share of the frame, and at census depth the deepened sky tint files in the BLACKISH channel-spread band without it). NO new shader features: the screen-door weave is CAST geometry (6 mm), and the floor camera rides the existing `fillShadeDepth`/`fillFromRig` vocabulary exactly as the garden's does. The set's signature is the weave's key light — a parallelogram of grid shadow combed across the deck that IS a prop (`prop:weaveShadow`, with `prop:gutterFlume`, in the callout registry); the gutter flume is laid AT deck height with its trickle as a timing tell, and `HAZARDS` ships EMPTY by ratification (the porch ladder pins the zero-live-zone law per rung; rain is deferred on treatment — Decision Log 2026-10-09).

The port's honest deltas vs ratified A: the sneakers are RESIZED 0.62× (at exploration scale they read as bricks at build camera), the hero rig is RE-AIMED at the door-mouth + step (medTone 155, the top of the ratified 131–155 high-key range), and the establishing frame is the ratified camera re-shot — its census row reproduces establishing-a's digit for digit (medTone 152, darks/blackish 0.000 %). Sockets are the threshold triple `door.in` / `door.out` / `step.out` (`PORCH_SOCKET_FRAMES`, all inside the deck disc; the door pair is test-pinned STAGING, travel axis ACROSS the lane — a ride needs ask #4's lane-crossing anchor). The guard split keeps the corridor buildable: door assembly + flume + stoam are SHELL (non-solid — a line may run through the door mouth as the garden lane crosses gravel), rails/posts/downspout/chime/lantern/planters/shoes are DRESS solids. Mounting is `porchSetPlacement` (five rows, derived by `tests/unit/porch-levels.test.ts`) at yaw 0 ON EVERY RUNG BY LAW — the weave must keep crossing the lane exactly as ratified, so the room never rotates for a level. Frames: docs/explorations/porch/production-build/-hero/-low.png at 1600×900 post-ON, census-clean (`tests/e2e/porch-set.spec.ts` smokes `?set=porch` and the kitchen no-regression boot).

## Invariants

- The set is a pure function of its inputs; the drawer sockets are derived from `DRESSER` position/yaw/`boreY` so the slit and the frames cannot drift.
- `?set=bedroom` (game shell) and `scene=bedroom-set` (harness) both render without console errors — `tests/e2e/bedroom-set.spec.ts` smokes both plus the kitchen no-regression boot.
- The punctual gate is a directional no-op: every pre-bedroom frame must stay byte-identical (the kitchen's visual baselines are the gate).
