# Modules/replay

> [!abstract] Role
> The determinism harness of brief §7.1: replay (level, build, seed) through `World` in Node, no GPU, and read the state hash. Owner: Systems Engineer.

## What it does

`src/replay/replay.ts` — `replayRun(level, build, { maxSteps?, launchSpeed?, record? })`: create the World with `visuals: false`, `launch()`, step until a terminal status or the fixed cap (default 15 s of sim time), return `{ hash, hashValue, steps, time, status }` and free the physics world. Termination depends only on the data, so equal inputs execute equal step sequences and must hash equal — which is the whole point. Since stage 5 `record: true` additionally returns `trace`: the per-step car transforms (`TraceSample` — the `state()` snapshot after each step, exact doubles), the Node side of the seek proof below; a plain replay is byte-for-byte the stage-2 call.

`src/replay/cinematic.ts` (stage 5) is the record the replay PAGE renders: `stepAndRecord(world, build, {maxSteps?, solids?})` launches a (usually visual) World and steps it to the terminal status, storing every step's car state — the very same list `replayRun({record:true})` yields, because both read `World.state()` after the same step order (visuals never reach the solver) — plus the §7.3 `RunCamera` follow pose advanced at `FIXED_DT`. Since the stage-5 readiness pass it is a one-shot WRAPPER over `TapeRecorder` — the same stepping code as a resumable state machine: `pump(n)` advances at most n fixed steps, `done`/`steps`/`totalSteps` read the wind, `sliceHashes` ledger the STATE HASH at every pumped boundary, and `finish()` assembles the `RunTrace` exactly as the old single loop did; slicing may only ever be a SCHEDULING decision (see below). `deriveEvents(samples, status)` (pure, used from both sides) prints the beats — Launch, Top speed (skipped when it is the first/last sample), Big air (the longest airborne segment ≥ 0.15 s, takeoff not landing), and the terminal beat; `planShots` cuts ≥ 3 contiguous shots tiling `[0, time + 0.9 s]` — a WIDE establishing (track bbox fitted to the 28° replay fov, look-at biased to the start, slow lateral drift), the tracked FOLLOW shot (the recorded per-step rail poses), and a FINISH lock-off at `cupView`'s capture centre on the approach tangent — with the cuts ON the beats and `REPLAY_BLEND` 0.4 s of eased cross-shots — and (playtest BB, "if the cuts actually ENDED on the cup-dunk I'd forward it") `planShots` holds the terminal cut early by `REPLAY_FINISH_LEAD` (0.4 s) whenever the shot ordering allows, so the cup-dunk happens INSIDE the held finish shot, never inside a blend into it. `ReplayDirector.poseAt(t)` is a pure function of sim time; inside the follow shot it IS the recorded pose of step `floor(t/dt)`.

The browser side of a replay is the shared-run page — `src/pages/share.ts` since the program-T0.2 extraction (boot still routes `#s=` here) — since stage 5 it OPENS INTO THE REPLAY. THE PAGE IS THE FILM (program T2.2 — THE FIRST TWO SECONDS): the stage is the first substantial node and paints its pre-wind preview frame as the page's first paint — the title (`#gw-replay-title`) is a caption, not a hero — with the replay bar (`#gw-replay-play`, `#gw-replay-time`, the `#gw-replay-timeline` scrub slider with event ticks, 1×/2×/4× `.gw-replay-speed`, and the `#gw-replay-build` "Build your own" exit to `?level=<id>`, which is ONE CLICK from first paint because the bar mounts before the wind) and, under the player, THE ONE HONEST VERDICT LINE `#gw-replay-verdict` (`role=status`, `aria-live`): it PROMISES while the tape winds ("replaying the run on this machine — the verdict lands when the tape is ready…") and PRONOUNS when the wind settles — `settle` says `✓ verified · matches the link — re-simulated on this machine` or `⚠ this machine disagrees · the replay here differs from the link`, machine-local by wording, the glyph riding the word (the old `#gw-replay-badge` pill is retired, not hidden; an unparseable link says "this link is not a run — nothing to replay" in the same line); below the fold the honest half — `parseShareUrl` → `getLevel` → the tape WIND → compare with the embedded hash → `verified`/`mismatch` in `#gw-replay-status` (the strings the specs read, unchanged), echoing the recomputed hash beside it, in `#gw-replay-verify` (since T2.2 the verification NOTE — the hash essay — lives inside a `#gw-replay-verify-fold` `<details>` toggle, closed by default, its `#gw-replay-verify-note` paragraph unchanged word-for-word: the essay moved, the mechanism did not), and the stage-3 share-card wiring (`#gw-share-card`) rides along there, reading the verdict LAZILY at click time (the run fields live in one mutable object the wind settles). Since the readiness pass the wind IS the verification: the chunked `TapeRecorder` run is the only simulation the happy path pays for, and `replayRun` survives only as the headless fallback verdict when the player cannot mount (a WebGL failure still must not eat the verdict). The player (`startReplayPlayer`) mounts the level's set + build in a visual World, winds the run step-for-step ACROSS SLICEs (see the readiness law below — the pump rides a `MessageChannel` port, `setTimeout(0)` only as its fallback, rAF only paints; playback never steps physics again), and renders the shot sequence through the house post stack (quarter-res tilt-shift, focus band on the car at the shown step). The seek law: the frame at t is the recorded SIM state at step `floor(t/dt)` — never a blend of two states; scrubbing cannot invent a state the sim did not produce. Autoplay starts on load (reduced-motion opens paused, blends collapse to cuts) — but a click made while the tape wound overrides the reduced-motion pause default. Autoplay is LEGAL on this page because the page RE-SIMS the run — it is not a media embed (program T2.2, the evaluation's own distinction; `Decision Log` 2026-10-09). PLAY always STARTS MOTION (playtest BB: "first Play click did nothing — second click worked"): the film LOOKS over long before it IS over — the finish tail (`REPLAY_TAIL`) and the last steps of the end crawl are watchable window with no watchable motion — so below `PLAY_RESUME_MIN` of remaining time a Play click REWINDS and plays instead of advancing the invisible sliver and re-pausing. CUTS CARRY THE SUBJECT (BB: "one ~0.5 s window shows an empty ground frame" — the blank lived inside the blend): through a cross-shot the blended pose gets a look-at nudge toward the car's traced position peaking at the midpoint as 4w(1−w), vanishing at both ends, so each shot's composed pose is untouched at its boundaries and the subject never leaves frame mid-cut. The player keeps a PACE LEDGER for the e2e (`__gwReplayPace`): [wallMs, playheadS, rate] per advanced frame, cleared at every seek/play/speed discontinuity — the clamped FINAL frame is never pushed but the clamp does NOT wipe the ledger (any continuation clears it at its own click), so a session that played the film out leaves its pure law-honouring frames for the probe even when CI frame pacing ended the window in 2–3 painted frames — the pacing-proof rate law `tests/e2e/share-replay.spec.ts` asserts (advance === min(frame gap, 0.25 s) × rate, PER RENDERED FRAME; the proof is 5 intervals OR every interval of a session that ended at the film's end), because CI truth (SwiftShader) can make a single frame outlast any wall-clock sampling wait and the old `waitForTimeout(300)` playhead snapshots went red off-step while passing 6/6 locally.

## Replay readiness — the chunked wind (feel pass, Playtest CC 2026-10-08 item (a))

CC's stranger opened a share link, clicked Play, and the tape only started ~6 s later — playhead pinned at the END meanwhile, button still reading "Play", so they double-clicked and gave up. Two full one-shot simulations (the `replayRun` verdict + the synchronous `stepAndRecord` fast-forward) sat between the click and the first frame, main-thread-blocked. The readiness pass makes the wait a SURFACE instead of a hole:

- **The bar is up-front WAITING** — before any heavy await `startReplayPlayer` puts `#gw-replay-play` on the bar with `data-phase="waiting"`, `aria-busy`, a spinner label counting the wind ("⏳ winding the tape… 40%", `#gw-replay-progress` beside it) and NO `aria-pressed` (a waiting button is not a toggled Play state); a preview wide frame of the rig paints while it winds. Progress runs against a par-derived step estimate, capped at 99 % until the run is genuinely over — it never claims ready early.
- **The wind is CHUNKED** — `TapeRecorder.pump(WIND_CHUNK_STEPS=32)` slices (≤ `WIND_CHUNK_BUDGET_MS=8` per slice) ride a **`MessageChannel` port** (a self-posted port message — a message-loop task, no timer to clamp), the 0 ms `setTimeout` kept only as the fallback for an engine without `MessageChannel`; **rAF only PAINTS** (the progress label, at most one paint in flight). The CI-red + hidden-tab fix: a frame callback can be STARVED, not just slow — CI's compositor paces it coarsely and Chrome stops firing rAF on a hidden tab ENTIRELY — and the old rAF-raced-16 ms-timer arm left the tape unwound there (the share-replay evaluate paid the wind and CI timed out at 30 s; a visitor backgrounding the tab never got the tape). Its `setTimeout(0)` replacement fixed the foreground but NOT the background — chained timers are CLAMPED when hidden, and intensive throttling aligns a tab hidden past ~5 min to ~ONE WAKE PER MINUTE, so an N-slice timer wind waits N minutes (close-review F-1). Chunks now progress on message tasks alone: item 4 of `tests/e2e/stage5-ready.spec.ts` asserts rAF-independence (rAF never fires, visibilityState hidden), item 5 asserts timer-clamp-independence (every page `setTimeout`/`setInterval` floored to one wake per minute — the CDP page-visibility override does not exist on this Playwright surface, so the floor IS the harness; the probe polls Node-side because every page clock is floored); the sim advances ~50 ms of work total across ~12 slices for kitchen01 par; per-slice state hashes are ledgered (`__gwReplayWind().chunks`). The trace/state seams only READ the recorded tape — no evaluate does synchronous catch-up — and the share specs await an explicit wind-phase READY poll (90 s) before their first evaluate. CI-truth repro on a GPU box: `E2E_SWIFTSHADER=1` (ANGLE SwiftShader, the CI renderer) × `E2E_STARVE_RAF_MS` (the specs' rAF-delay harness) — see [[Sessions/2026-10-10 Stage 5 - BB feel fixes]].
- **A click during the wind is QUEUED, never swallowed** (`__gwReplayWind().pendingPlay`), and on ready the playhead SNAPS to 0 and rolls without a second click. The button ledger `__gwReplayPhases()` must read waiting → (queued-click) → playing → ended. The waiting state is FORCED in the spec, not raced (close-review F-2): the dev-only `?e2eWindSlice=N` debug param pins the pump to exactly N steps per scheduled tick (budget dropped) and an init-script clicker presses the button in the microtask its DOM append schedules — so the queued-click proof runs on EVERY machine, no `if (clickedWhileWaiting)` skip.
- **Determinism, extended**: slicing is only scheduling — the trace and the TERMINAL hash equal the one-shot `replayRun` result (the existing gate), and every slice boundary carries the state hash the one-shot Node sim has after the same step count — asserted slice by slice in `tests/e2e/stage5-ready.spec.ts` item 3 against a `World` stepped to the same boundaries, and in `tests/unit/cinematic.test.ts` (7-step slices + slice-hash equality at every boundary).

Measured (this box, headless Chromium): the waiting bar is up by ~150 ms; the tape is wound and the verdict settled by ~300 ms of slice clock; first painted frame ~1.2 s (the one remaining block is the software GL's one-time post-stack shader compile, ~870 ms here, which now lands inside the honest WAITING window rather than behind a dead button); playhead at 0 on ready, at the terminal time ~3 s of watching. The 6-second silence is gone. The e2e ready bound is asserted CI-tolerantly (4 s) because headless CI pays the shader compile; the 1.5 s feel target is met on hardware GL where that compile is ~10× cheaper.

What the hash COVERS, stated precisely (playtest F's "different builds, same hash" finding): `hashBodies` folds the quantised transforms of the RUN'S CAR BODIES (chassis + wheels, `world.hashedBodies`) every `HASH_INTERVAL` steps into the seed-folded accumulator — static track bodies are never hashed directly. Two builds are therefore guaranteed equal-hash exactly when the car's sampled trajectory is equal; a piece that sits OFF the car's road (a static the run never touches) cannot perturb the hash, and the shell's panel may say so truthfully ("same run — your extra piece never touched the road", `#gw-hash-note`).

## The solid-red replay stage (playtest AA, 2026-10-10)

Playtest AA saw a hand-forged `#s=` link play with an honest verdict while the stage rendered SOLID RED. Diagnosis (`Sessions/2026-10-10 Stage 5 - replay red diagnosis`): the 1.3 s tape was a build with nothing under the release — status `fell` at 0.4 s — so the finish shot had no `cupView` and took `finishTangent` from the last 24 samples: exactly vertical. In `ReplayDirector`'s finish pose the terms `tangent*-0.45d + UP*0.42d` then cancel to (0.45−0.42)·d ≈ 3 cm — the eye INSIDE the red chassis (`#d7263d`), whose interior filled the frame maroon for the whole finish hold (measured: 98.4 % of pixels in the car-chassis colour band at the playtesters' playhead; machine-independent geometry, not a GPU bug). The guard: a near-vertical final tangent (|y| > 0.95) is flattened onto the floor plane before `finishRight` is built — a vertical vector is not a camera direction. The offset after the guard is d·|0.45,0.42| ≈ 0.68 m; the census re-runs at 0.7 %. Kitchen01 par frames sit at ≤ 2.7 % band-share (that is the car and track orange at honest framings), so the e2e censors at 40 %.

## Ghost racing — a trace, not a simulation (program T3.2, 2026-10-09)

The deterministic guarantee IS the feature: a ghost car beside yours (`src/pages/ghost.ts`, laws and surface in [[ui]]) costs exactly one headless `TapeRecorder` wind of a build you are not driving — `deriveGhostTrace` pumps the SAME resumable stepping the share page chunked (slices on `MessageChannel` tasks, scheduling-only per the chunking law above) against a `visuals: false` world and keeps the per-step `pos`/`quat` list that `replayRun({record:true})` yields — asserted equal step-for-step in `tests/unit/ghost.test.ts`. No second World races the player's: the ghost reads the live sim's clock (`sync(world.time)`) and never steps physics, so with the ghost ON the page's run hashes byte-identical to the Node replay (asserted live in `tests/e2e/ghosts.spec.ts`) and `npm run replay:all` stays 30/30 verified (run at this lane's HEAD). THE MEASURED ORDER LAW: the plan's prerequisite probe was run, not assumed — `scripts/probe-piece-order.mjs` replays every registered level's reference build under 4 deterministic piece-ARRAY permutations under BOTH senses of “permuted”: `seq` KEPT (148/148 identical — the mechanism is `canonicalBuild`'s sort by `seq` inside `reify`) and permuted-and-RENUMBERED, array order becoming canonical order (148/148 identical too — hash AND step count, consistent with `hashBodies` folding only the car's bodies, never the static track's). So permuted-but-same builds may be called equal anywhere, including cross-machine; the PAR ghost never needed the claim (it winds the canonical `parBuild()` array itself), and a FRIEND ghost needs only that the payload's build, once deserialised, is canonical bytes — which the share layer already guarantees.

## Replay-all gate (stage 5)

`npm run replay:all` (`tools/replay-all.mjs`) walks the campaign ladder IN ORDER and replays every
rung's `parBuild()` twice in Node — both runs must FINISH, hash EQUAL (that pair is the
determinism claim per rung, not just per rig), respect `pars.json` parTime, and place exactly
`parPieces` PLAYER pieces (fixtures excluded via the one `fixtureQuota` rule, the same arithmetic
`playerPieceCount` does in `src/ui/advice.ts`). All 26 rungs verified at landing; the table honestly shows
IDENTICAL hashes across rooms sharing a deck (bathroom/garden/garage 01 run on kitchen01's
physics — the port doctrine made decks reusable, hashes prove it) — the same fact that makes the
F6 save-stamp deferral matter. The step runs in CI after typecheck.
